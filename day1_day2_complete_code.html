lib/db.ts

Connects your app to MongoDB Atlas. Called at the top of every API route before any database query.

1
import mongoose from 'mongoose';

mongoose is the library that lets you talk to MongoDB from Node.js. It gives you Schemas (data shape), Models (query interface), and connection management. Without this import, nothing database-related works.

⚠ Remove this: every line below throws "mongoose is not defined". Run npm install mongoose if you get "Module not found".

3
const connect = async () => {'{' }

Defines an async function called connect. async is required because mongoose.connect() returns a Promise — it takes time to establish a network connection and we need to wait for it with await.

⚠ Remove async: you can't use await inside, mongoose.connect() fires but your code continues before the connection is ready — every query below it fails.

4
if (mongoose.connection.readyState >= 1) return;

readyState is 0=disconnected, 1=connected, 2=connecting, 3=disconnecting. If already connected (≥1), skip creating a new connection and return early. This is the connection caching pattern — critical because Next.js API routes are serverless functions that restart on every request.

⚠ Remove this line: every single API call creates a brand new MongoDB connection. In production you'll hit Atlas's 500-connection free tier limit within minutes of real traffic and all queries start failing.

5
await mongoose.connect(process.env.MONGO_URI!);

await pauses until the TCP connection to MongoDB Atlas is established. process.env.MONGO_URI reads the value from .env.local — never hardcode credentials. The ! is TypeScript's non-null assertion — you're telling TS "trust me, this env var exists".

⚠ Remove await: the function returns before connecting — first query throws "MongooseError: operation buffering timed out". Remove !: TypeScript error "Argument of type 'string | undefined' is not assignable". Wrong MONGO_URI: connection throws and crashes the route.

7
export default connect;

Exports the function so other files can import and call it. Every API route starts with: import connect from '@/lib/db'; await connect();

⚠ Remove export: no other file can import connect — every route that needs the DB has to re-implement the connection logic from scratch.

⚠ Skip importing models: in Next.js dev mode, file hot-reload re-runs this file on every save. Calling model('User', schema) twice throws "Cannot overwrite User model once compiled" and crashes the server.

⚠ Remove this and define fields directly in model(): you lose validation, type coercion, and all Mongoose middleware hooks — data quality becomes your problem to manage manually.

4

app/api/auth/register/route.ts

Creates a new user account. Hashes the password, saves to MongoDB, sets a JWT cookie.

1
import {'{'} NextRequest, NextResponse {'}'} from 'next/server';

NextRequest is Next.js's enhanced Request object with cookie helpers, geo data, and IP info. NextResponse is how you send responses — has .json(), .redirect(), .cookies.set(). These replace Express's req/res.

⚠ Try to use Express's res.json(): "res is not defined" — you're not in Express. This is Next.js Route Handlers — always return NextResponse.

7
export async function POST(req: NextRequest) {'{'}

The function name POST (uppercase) tells Next.js to call this when a POST request hits /api/auth/register. The file path defines the URL — app/api/auth/register/route.ts → /api/auth/register. You can export GET, POST, PUT, DELETE, PATCH in the same file.

⚠ Name it lowercase 'post': Next.js ignores it — all POST requests return 405 Method Not Allowed. Name the file handler.ts instead of route.ts: Next.js doesn't recognise it — 404 on all requests.

8
await connect();

Connects to MongoDB before anything else. In Next.js serverless functions, each invocation may start completely fresh with no DB connection. The readyState check in db.ts makes this a no-op if already connected.

⚠ Remove this line: User.create() throws "MongooseError: operation buffering timed out after 10000ms" because there's no active connection to send the query to.

9
const {'{'} email, password {'}'} = await req.json();

req.json() parses the request body as JSON — returns a Promise so we await it. Destructuring pulls out email and password. This replaces Express's req.body which needed the express.json() middleware.

⚠ Use req.body instead: undefined in Next.js Route Handlers. Forget await: you get a Promise object, not the parsed data — email and password are both undefined and bcrypt.hash(undefined) throws.

10
const hash = await bcrypt.hash(password, 10);

bcrypt.hash() runs the password through the bcrypt algorithm 2^10 = 1024 times (salt rounds = 10). The output is a 60-character string that looks nothing like the input. It's one-way — you can never reverse it. This takes ~100ms intentionally — making brute force attacks slow.

⚠ Skip hashing and store plain password: if your database is ever breached, every user's password is exposed. Salt rounds above 12: each register call takes seconds — serverless functions time out. Salt rounds below 8: too easy to brute force.

11
const user = await User.create({'{'} email, password: hash {'}'});

User.create() inserts a new document into the users collection and returns the saved document including its auto-generated _id. We pass hash (not password) — the raw password is never stored. If email already exists, MongoDB throws E11000 duplicate key error.

⚠ Pass password instead of hash: plain text stored in DB — critical security vulnerability. No try/catch around this: duplicate email crashes the handler with a 500 instead of a friendly "Email already exists" message.

12
const token = jwt.sign({'{'} id: user._id {'}'}, process.env.JWT_SECRET!, {'{'} expiresIn: '7d' {'}'});

jwt.sign() creates a JWT — a signed string containing the payload {'{'} id: user._id {'}'}. The JWT_SECRET signs it so you can verify it hasn't been tampered with. expiresIn: '7d' makes it invalid after 7 days. We only store the user's _id in the payload — nothing sensitive.

⚠ Put password or email in the payload: JWT payloads are base64 encoded, not encrypted — anyone can decode them at jwt.io. expiresIn: '100y': tokens never expire — a stolen token works forever. No JWT_SECRET: jwt.sign() throws, route returns 500.

13-14
const response = NextResponse.json({'{'} success: true {'}'}); response.cookies.set('token', token, {'{'} httpOnly: true, maxAge: 604800 {'}'});

httpOnly: true means the cookie cannot be read by JavaScript (document.cookie returns nothing) — only sent automatically by the browser on every request. This prevents XSS attacks from stealing the token. maxAge: 604800 = 7 days in seconds — matches JWT expiry.

⚠ Store token in response body and save to localStorage instead: XSS attacks can steal it with document.cookie. httpOnly: false: same problem. In production, also add secure: true so the cookie only travels over HTTPS.

app/api/auth/login/route.ts

Verifies email + password against the database, issues a new JWT cookie on success.

9
const user = await User.findOne({'{'} email {'}'});

findOne({'{'} email {'}'}) searches the users collection for the first document where email matches. Returns the full user object (including hashed password) or null if not found.

⚠ Use findById() instead: you don't have the ID at login time — only the email. Use find() instead of findOne(): returns an array, not a single user — bcrypt.compare(password, user[0].password) gets messy.

10
if (!user || !await bcrypt.compare(password, user.password))

!user — email doesn't exist in DB. bcrypt.compare(password, user.password) — re-hashes the submitted password and checks if it matches the stored hash. Returns true/false. Combining both checks in one if statement is intentional — the error message is identical for both cases (security through obscurity — don't tell attackers whether the email exists).

⚠ Return different errors for "email not found" vs "wrong password": attackers can enumerate valid email addresses by trying different emails and watching the error. Always return the same "Invalid credentials" for both cases.

11
return res.status(401).json({'{'} error: 'Invalid credentials' {'}'});

401 Unauthorized is the correct HTTP status for "you didn't authenticate correctly". 403 would mean "authenticated but not allowed" — wrong here. 400 would mean "bad request" — also wrong. HTTP status codes carry semantic meaning.

⚠ Return 200 with an error message: the frontend's if (!res.ok) check won't trigger — it'll try to redirect to /dashboard even though login failed. Always use correct HTTP status codes.

middleware.ts

Runs before every /dashboard request. Checks the JWT cookie — redirects to /login if missing or invalid.

Why middleware instead of checking auth inside the page? If you check auth inside dashboard/page.tsx, the page starts rendering, data starts loading, then the redirect fires — user sees a flash of protected content. Middleware intercepts the request before any page code runs — redirect is instant and clean.
2
import {'{'} jwtVerify {'}'} from 'jose';

jose is a Web Crypto API-based JWT library. It works in Edge Runtime (the environment middleware runs in), browsers, Deno, everywhere. jsonwebtoken uses Node.js crypto which isn't available in Edge Runtime.

⚠ Import from 'jsonwebtoken' instead: "The edge runtime does not support Node.js 'crypto' module" — middleware crashes on every request. Always use jose specifically in middleware.ts.

4
export async function middleware(req: NextRequest) {'{'}

Must be named exactly middleware (lowercase) and exported as a named export — not default. Next.js looks for this specific export in middleware.ts at startup. This is a framework convention.

⚠ Name it authMiddleware or export default: Next.js can't find it — middleware silently never runs, every route is unprotected. This was your exact bug — fixed by restarting npm run dev after creating the file.

5
const token = req.cookies.get('token')?.value;

req.cookies.get('token') reads the httpOnly cookie named 'token'. The ?. optional chaining returns undefined instead of crashing if the cookie doesn't exist. .value extracts the string from the cookie object.

⚠ Try to read from localStorage here: middleware runs server-side — localStorage is browser-only. req.cookies is the only way to read auth tokens in server-side middleware.

6
if (!token) return NextResponse.redirect(new URL('/login', req.url));

If no token cookie — user isn't logged in. new URL('/login', req.url) builds a full URL using req.url as the base — works in both localhost:3000 and production domains without hardcoding.

⚠ Hardcode NextResponse.redirect('http://localhost:3000/login'): in production all users get redirected to localhost — app breaks entirely for real users. Always use new URL('/path', req.url).

8
await jwtVerify(token, new TextEncoder().encode(process.env.JWT_SECRET!));

jwtVerify() decodes the token and verifies its signature using the secret. new TextEncoder().encode() converts the JWT_SECRET string into a Uint8Array — jose requires the key as bytes, not a plain string (unlike jsonwebtoken which accepts strings).

⚠ Change JWT_SECRET after users have registered: every existing token fails verification — all users get logged out instantly. Skip TextEncoder: jose throws "Key must be a CryptoKey or a Uint8Array" — all requests redirect to /login even with valid tokens.

14-16
export const config = {'{'} matcher: ['/dashboard/:path*'] {'}'};

matcher tells Next.js which routes this middleware applies to. /dashboard/:path* matches /dashboard and any sub-path. Without this, middleware runs on every request including /_next/static/ CSS/JS files.

⚠ Remove matcher: middleware runs on every request including static assets — all CSS/JS files get redirected to /login — app is completely broken and unstyled. Include /login in matcher: redirect loop — /login redirects to /login forever.
